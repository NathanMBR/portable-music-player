# Portable Music Player UI

This Storybook is the detailed documentation of the player's interface. Every component has a
`*.stories.tsx` file next to it. Its Docs page describes what the component is for, lists its props
(read from the JSDoc in the component's source) and shows one story per situation it handles. The
**Design tokens** page covers colors, type and interaction states.

## The app shell

`App` fills the window with the view of the current category. `App` maps each category id to its
view (`viewByCategory`), so the navigation feature never imports the views it switches between.

- **Margins:** the view keeps equal side margins, sized by the `gutter` token (`px-gutter`). The
  menu button sits in the left one, so views never include it and nothing scrolls under it.
- **Scrolling:** the window itself never scrolls. A view keeps its header in place and scrolls
  only the content below it. The app draws its own scrollbar, in the right margin beside the
  content, and the content keeps the width between the margins. The content reaches the window's
  bottom edge, or ends above the player while it's open.

The **audio player** (`AudioPlayer`) slides up along the bottom of the window when a song is played,
and away when it's stopped. `App` renders it outside the views, so a song keeps playing when the
category changes. It holds shuffle, previous, play or pause, stop, next and repeat on the left, the
song's title above its progress bar in the middle, and the speaker and volume on the right. The bar
has the elapsed time on its left, which a click turns into the time left counted down, and the
song's length on its right. The progress stops growing at a set width, so in wide windows the
spaces around it widen instead.
Clicking the speaker mutes, and clicking it again brings the volume back, and the mouse wheel over
the volume turns it up or down by 5%. The views end above its
space, and while it's open notifications pop up above it, both sized by the `player` token. The
progress bar is a slider: clicking or dragging it jumps within the song. Past a song's first 3
seconds, previous starts it over. A song's length shows as `--:--` while its audio loads, and when
the last song ends without repeat, it stays in the player, paused at its start.

The **notification area** (`NotificationArea`) sits in the bottom-right corner, above everything,
the side menu included. Notifications pop up there, close by themselves after a few seconds or
earlier with their × button, and pause while hovered.

The **side menu** is an overlay drawer (`SideMenu`) opened by the menu button. It lists the
categories from `src/features/navigation/categories.ts` and holds the theme toggle. Choosing a
category switches the view and closes the drawer. Adding a category takes one entry in `CATEGORIES`
and one view in `viewByCategory`.

The only category so far is **Songs** (`LibraryView`): a header with the song count, which stays in place while the list scrolls, then the
song list, a notice for an empty Songs folder, or a calm notice with "Try again" after a failed
scan. Each song starts with a `PlayButton`, which plays it in the audio player with the whole list
as the queue.

## Where the code lives

- `src/components/`: feature-agnostic building blocks (`Button`, `IconButton`, `Notice`, `Slider`),
  built on Headless UI and styled with Tailwind, each in a folder of its own with its stories.
  `buttonStyles.ts`, beside the folders, holds the looks and states every button shares: the
  `quiet`, `outlined` and `filled` variants, the active look, focus and disabled.
- `src/features/notifications/`: the notification area and `notify.ts`, the only module that calls
  Sonner, the toast library behind the notifications.
- `src/features/<feature>/`: everything one feature owns. Its types mirror the Rust structs,
  `<feature>Api.ts` is the only file that calls Rust, `<feature>Store.ts` is its Zustand store, and
  each of its components sits in a folder of its own with its stories.

## How data flows

A component reads its state from a Zustand store and calls the store's actions. The store calls its
feature's `*Api.ts`, which uses Tauri's `invoke()` to run a Rust command. The Rust commands read
and write the `Songs` folder and the `.json` files next to the executable, so everything stays on the
flash drive.

Rust errors reach the frontend as their message string. The store that caught one calls
`notifyError(title, error)`: the title says what failed, and Rust's message, shown as it is, says
why. Raising the same failure again replaces the notification on screen instead of stacking a copy.
The view itself never shows red text: when a failure leaves it with nothing to show, like a failed
scan, it shows a calm `Notice` with what to do next.

Songs play through one more loop. `songAudio.ts`, connected once from `main.tsx`, is the only
module that touches the audio. It follows the playback store's song, play state, position and
volume, and reports the song's length, progress and end back to the store, which decides what plays
next. Between the audio's own reports the progress runs on with the clock, because on Linux the
audio's clock can hold still for seconds while the song plays on. To load a song it asks Rust where the song plays from (`song_source`). On Linux the song
streams from a small HTTP server that Rust runs for this computer only, because the Linux webview
skips ahead in large songs played from memory. On Windows Rust sends the song's file as raw bytes
(`read_song`), and the audio plays them from memory, through an object URL. Neither webview can
stream audio from Tauri's own file URLs. A song that can't play raises "Couldn't play" with its
title, and the player pauses on it. Before loading, it asks the webview whether it can play MP3 at
all: on Linux, a webview missing GStreamer's plugins freezes the app instead of reporting an error,
so the player stops there and says what to install.

`windowTitle.ts`, also connected once from `main.tsx`, names the window after the song in the
player, playing or paused, and after the app once it's stopped.

`mediaSession.ts`, connected once from `main.tsx` too, hands the song in the player to the system
through the webview's media session, so the keyboard's media keys and the system's media controls
play, pause, stop, skip and seek it. WebView2 passes it on to Windows' media controls, and
WebKitGTK to MPRIS on Linux. It gives the song's title and play state only when they change, and
leaves the position to the webview, which reads it from the audio. Webviews without a media
session, like WebKitGTK before 2.46, simply don't get one.

## How the stories run without Tauri

Storybook runs the UI in a plain browser, where there is no Rust side. Three pieces make the stories
work anyway:

- **Fake commands.** `mockCommands` (`src/testing/mockCommands.ts`) answers Rust commands through
  Tauri's own `mockIPC`. Each story mocks the commands its interactions trigger, which also
  documents the commands a component uses. A command that isn't mocked rejects with
  `Unmocked command: <name>`, and `failingCommand(message)` fakes a Rust error.
- **Fresh stores.** Before every story, `resetStores` puts every store back to its initial state and
  dismisses every notification. A story then sets the state it shows in its `beforeEach`, for
  example a failed scan. Stories of a component that raises notifications render the notification
  area next to it with the `withNotificationArea` decorator.
- **One frame per story on Docs pages.** The stores are shared by everything on a page, so stories
  that set store state render in their own iframe there (`renderInOwnFrame`), and don't overwrite
  each other's state.

Stories never connect the audio (`songAudio.ts`), the window title (`windowTitle.ts`) or the media
session (`mediaSession.ts`), so they're silent: the player shows whatever progress and length the
story puts in the store.

The **theme** toolbar switches `data-theme` on `<html>` between `light` and `dark`, like the app's
own toggle does.

## Stories are tests

`pnpm test:ts:storybook` runs every story as a Vitest test in headless Chromium:

- the story must render without errors;
- its `play` function, if any, must pass (e.g. clicking "Try again" brings the songs back);
- the axe accessibility check must find no violations.

The pure logic and the stores have their own unit tests (`*.test.ts`), and the Rust side has its
own tests (`pnpm test:rs`). `pnpm test` runs all of them.
